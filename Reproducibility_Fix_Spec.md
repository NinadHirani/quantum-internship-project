# Reproducibility Fix Spec — Quantum Vehicle Routing Project

## How to use this document
This is a **bug-fix spec**, not a feature spec. The project's architecture and math are correct and all 17 existing tests pass — but the pipeline is not actually reproducible end-to-end as committed. Execute the tasks below in order; each has a concrete acceptance check. Do not touch unrelated code, formulation, or docs beyond what's specified here.

Audit method: fresh clone, `pip install -r requirements.txt`, `pytest tests/ -v`, `python run_all.py`. Findings below are from that run, not guesses.

---

## Task 1 — Fix missing dependency in `requirements.txt`

**Problem:** `src/quantum/qaoa_solver.py` imports `from qiskit_algorithms import QAOA`, but `qiskit-algorithms` is not listed in `requirements.txt`. On a clean install, `import src.quantum.qaoa_solver` fails immediately with `ModuleNotFoundError`, which means `tests/test_qaoa_solver.py` cannot even be collected and `run_all.py` cannot run past Step 3.

**Fix:**
- Add `qiskit-algorithms>=0.3` to `requirements.txt` (pin the version actually used in dev/test — check installed version with `pip show qiskit-algorithms` before pinning).
- Re-run `pip install -r requirements.txt` in a **fresh** virtualenv (not the existing dev one) to confirm nothing else is silently missing.

**Acceptance check:**
```bash
python -m venv /tmp/verify-venv && source /tmp/verify-venv/bin/activate
pip install -r requirements.txt
python -m pytest tests/ -v
```
All 17 tests collect and pass with zero `ModuleNotFoundError`.

## Task 2 — Regenerate `results/benchmark_table.csv` so it matches current code

**Problem:** The committed `results/benchmark_table.csv` shows a QAOA run at **17 qubits, p=1**, infeasible, no total_distance. Running the current `run_all.py` with **default** arguments produces a **24-qubit, p=2** QUBO (penalty weights ~360 vs. the 300 implied elsewhere). The committed CSV was generated by a different code/param state than what's in the repo now — it does not describe the current pipeline and should not be trusted or cited in `docs/report.md`.

**Fix:**
- Decide the canonical default configuration for the checked-in results (recommend: keep `--customers 4 --qaoa-layers 2 --seed 42` as the README already documents these as defaults — so the CSV should reflect a p=2, 24-qubit run, not the current stale p=1/17-qubit one).
- Re-run `python run_all.py` with that canonical configuration end-to-end (see Task 3 for the runtime problem you'll hit) and overwrite `results/benchmark_table.csv` with the fresh output.
- Cross-check `docs/report.md` section(s) that cite benchmark numbers (qubit count, feasibility, distance, runtime) and update any numbers that no longer match the regenerated CSV.

**Acceptance check:**
`results/benchmark_table.csv` qubit_count for the QAOA row matches what `build_cvrp_qubo` actually returns for the documented default config, and every number cited in `docs/report.md` matches that CSV exactly (no stale figures left over from an earlier formulation).

## Task 3 — Make the QAOA step in `run_all.py` actually finish (or document why it can't at default settings)

**Problem:** Running `python run_all.py` with default settings (4 customers → 24-qubit QUBO from position encoding, p=2, statevector simulator) did not complete Step 4 (QAOA) within 280 seconds — the "one-command full pipeline" promised in the README is currently unverified past Step 3 (QUBO/Ising construction) on realistic hardware/time budgets.

**Fix — pick ONE of these, don't half-do both:**

- **Option A (reduce default problem size):** Lower the default `--customers` count or switch the default encoding so the out-of-the-box `run_all.py` finishes in a few minutes on a laptop CPU. Only change the *default*; keep the flag so larger instances are still opt-in. State the new default runtime in the README.
- **Option B (keep the size, fix the runtime honestly):** Leave defaults as-is, but (1) add a progress callback / iteration logger to `qaoa_solver.py` so the optimizer's progress is visible instead of a silent multi-minute hang, (2) add a `--max-iter` flag to cap the classical optimizer's iterations so runtime is bounded and predictable, and (3) update the README to state the real expected runtime for the default config (e.g. "~X minutes on a standard CPU for 24 qubits, p=2") instead of implying it's fast.

**Acceptance check:**
`time python run_all.py` completes without a manual timeout, and the printed runtime is within what the README now claims.

**Fix:**

**Acceptance check:**
`git status` after a full `run_all.py` run shows the new figure files as trackable (not ignored), and `results/figures/` in the repo has more than just `.gitkeep`.

## Task 5 — Resolve or clearly scope `milp_solver.py`

**Problem:** `src/classical/milp_solver.py` is a 22-line stub that raises `NotImplementedError`. The README already marks MILP as a "stretch goal," so this is not a blocking bug — but confirm it's not silently imported/called anywhere in `run_all.py`, `compare.py`, or the tests in a way that would crash a real run.

**Fix:**
- Grep the codebase for any call site of `milp_solver`. If none exist outside its own file, no code change needed — just leave a one-line comment in `milp_solver.py` confirming it's intentionally unimplemented (stretch goal, not required for the four-milestone gate plan).
- If it IS called anywhere in the main pipeline, either implement it or remove the call before Task 3's full-pipeline run.

**Acceptance check:**
`grep -rn "milp_solver\|solve_cvrp_milp" --include=*.py .` shows no call sites outside `milp_solver.py` and its own test file (or, if there are call sites, they're now handled without crashing).
